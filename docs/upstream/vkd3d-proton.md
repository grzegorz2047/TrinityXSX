## Before anything is submitted

vkd3d-proton's pull request template (`.github/pull_request_template.md`) asks the author to confirm two
things: "I have not copy-pasted an LLM-generated response into the description" and "I am able to
explain and understand the code I have submitted". The issue templates ask for the first one as well.

These drafts were written with an LLM, and the patches carry a `Co-Authored-By: Claude` line. Use the
texts below as notes. Write the final description in your own words, and submit only code you can
explain in review. dxil-spirv has no template, but the same applies there.

# dxil-spirv (HansKristian-Work/dxil-spirv)

PR titles there are plain imperative sentences, sometimes prefixed `dxil:` (for example
"Look up resource extended properties by tag", "Support struct return for legacy udiv.",
"dxil: Always decorate FMad's FMA as NoContraction"). Tests are HLSL files under `shaders/`, with
expected output in `reference/shaders/`, generated by `./test_shaders.py shaders --dxc … --dxil-spirv …
--update`. Hand-written modules go in `shaders/asm/`:

- `*.bc.dxil` is a raw LLVM bitcode module, run with `--raw-llvm`;
- `*.dxil` is a DXIL container;
- only files ending in `.dxil` (or `.dxbc`) are treated as asm; anything else is compiled with DXC
  as HLSL;
- the asm tests also run with `--ssbo-uav --ssbo-srv --enable-shader-demote
  --min-precision-native-16bit --assume-ssbo-32bit-wrapping` (`test_shaders.py`).

## 0001 – UDiv helpers typed by the result struct: fixed upstream

- **Ours:** `emit_dxbc_udiv_instruction()` built the `UDiv`/`UMod` helpers with the instruction's
  result type, the `{quotient, remainder}` struct. We switched to the type of operand 1.
- **Upstream (#370, `34f0ff84`):** the same change (`arg_type_id` from operand 1). It also builds the
  result with `OpCompositeConstruct` of the instruction's own type, where we kept the old
  `build_vector`. #370's description links vkd3d-proton issue #3501 and quotes the same form:
  `call %dx.types.twoi32 @dx.op.binaryWithTwoOuts.i32(i32 43, …)`.
- **Our evidence:** `docs/STATUS.md` records invalid SPIR-V and a crash in NVIDIA's driver while it
  compiled the pipeline. No dump or log of that case was kept in `analysis/`.
- **Verdict:** nothing to submit. Upstream has no reference test for this op (#370 changed only
  `dxil_arithmetic.cpp`); see the optional test PR below.

## 0002 – structured stride read positionally from the tags: fixed upstream

- **Ours:** `get_structured_stride_from_tags()` walks the (tag, value) pairs and takes tag 1. It is
  used in `emit_srvs()`, `emit_uavs()` and `get_raw_buffer_meta()`.
- **Upstream (#372, `7f5a7780`):** `get_resource_tag()` with a `ResourceTag` enum, used at the same
  three places. It also handles the typed-buffer element type (tag 0), which was also checked by
  position (`get_constant_metadata(tags, 0) == 0`). Our patch did not touch that. #372 adds
  `resources/sm66/atomics-64bit-raw-access.root-descriptor.sm66.comp`.
- **Our evidence:** XCL's direct DXIL emitter writes the tags the upstream test describes
  (only `{ Atomic64Use, 1 }`). From `analysis/atomics/0c33406ba7854c90.dxil.ll`:

  ```llvm
  !8 = !{i32 1, %struct.RWByteAddressBuffer* undef, !"", i32 0, i32 2, i32 1, i32 11, i1 false, i1 false, i1 false, !9}
  !9 = !{i32 3, i32 1}
  ```

  The buffer is bound as a root UAV: every parameter in `6af36c95f665a4d6.rs` has type 4. Before the
  fix, the SPIR-V added the undef element offset to the address (`%26 = OpIAdd %uint %25 %24`, with
  `%24 = OpUndef %uint` in `0c33406ba7854c90.spvasm`).
  - `raw_and_structured_buffer_atomics_run` failed (`left: 0, right: 3856`,
    `analysis/atomics/test.log`).
  - `gpu_more_atomics_sub_dword_scratch_valu` was still running after 60 s (`analysis/hang/hang.log`;
    that shader came from XCL's recompiler through DXC and carries the same `!{i32 3, i32 1}` tags).
  - With the patch, both passed (`analysis/after/*/test.log`).
- **Verdict:** nothing to submit. Upstream's test covers the same tags on the same root-descriptor path.

## 0003 – UAddc / USubb: fixed upstream

- **Ours:** a special case in `emit_dxil_wide_arith_instruction()`. It computes `OpIAddCarry` /
  `OpISubBorrow` into `{ uint, uint }`, keeps the member order, turns member 1 into a bool with
  `OpINotEqual`, and constructs the DXIL `{ i32, i1 }`.
- **Upstream (`79b870bb`):** a separate `emit_dxil_wide_arith_instruction_add()`, which does the same
  (`ext_lo`, `ext_carry`, `OpINotEqual`, `OpCompositeConstruct`). `opcodes_dxil_builtins.cpp` maps
  both `UAddc` and `USubb` to it.
- **Our evidence:** `analysis/uaddc/test.log`, before the fix: `lane 0: 0x0 0x9e3779b9`,
  `left: [0, 1, 1, 1]`, `right: [2654435769, 0, 1640531527, 1]`. The value and carry slots came out
  swapped. With the patch, the test passed (`analysis/after/uaddc_and_usubb_match_cpu/test.log`).
- **Verdict:** nothing to submit. Upstream's test (`add64.comp`, through `AddUint64`) covers UAddc
  only. USubb uses the same function with `OpISubBorrow`, and no DXIL test covers it (a code search
  of the upstream repository finds `OpISubBorrow` only in `reference-dxbc/`, the DXBC frontend's
  references).

# vkd3d-proton (HansKristian-Work/vkd3d-proton)

Commit subjects there use a component prefix and end with a period: `vkd3d: …`, `vkd3d-shader: …`,
`tests: …`, `dxil-spirv: Update submodule.`, for example "vkd3d: Fix atomic issues on 32-bit MSVC."
and "tests: Fix a VVL mute for r16 texel buffer atomic test.". PR titles are either such a subject
or a short plain sentence ("Rewrite how viewports and scissors are emitted"). To build the tests, use `-Denable_tests=true`. Select tests with `VKD3D_TEST_FILTER` /
`VKD3D_TEST_MATCH` (README).

## 0001 – `VKD3D_VTBL_IS()`: not suitable

What it does: every `lpVtbl == &…_vtbl` identity check and `impl_from_*()` assert in `libs/vkd3d` also
accepts an object whose `lpVtbl[-1]` is vkd3d-proton's vtable.

Why not upstream:

- It exists only because XCL replaces the vtable pointer of objects that vkd3d-proton created with an
  extended copy (`xcl/crates/xcl/src/hle/d3d12x/real.rs`: `ext[-1]` holds the original). vkd3d-proton
  uses those checks to tell its own objects from foreign ones, for example in
  `d3d12_command_list_from_iface()` on submission. An object modified this way is outside what a
  D3D12 implementation can be expected to support.
- `lpVtbl[-1]` is read for every vtable that is not vkd3d-proton's. For a foreign object, that is
  memory vkd3d-proton knows nothing about. With MSVC C++ objects built with RTTI it is the RTTI
  locator. Elsewhere it
  can be anything, including the end of an unmapped page.
- The comment it adds to `vkd3d_private.h` names XCL. Such a check could not be justified for any
  other application.
- The asserts are already compiled out with `-Db_ndebug=true`. What remains are the lookups that
  return NULL for a foreign object (`d3d12_command_allocator_from_iface()`,
  `d3d12_bundle_allocator_from_iface()`, `d3d12_bundle_from_iface()`,
  `d3d12_command_list_from_iface()`) and the result of `is_shared_ID3D12Fence1()`.

The patch keeps XCL working on vkd3d-proton (`docs/STATUS.md`: without it, `CreateCommandList`
returned `E_INVALIDARG` and `ExecuteCommandLists` crashed). Keep it downstream, or change how XCL
adopts objects, for example by restoring the original vtable pointer, or wrapping instead of swapping,
for objects that go back into the runtime. Do not open an issue for it unless XCL cannot be changed.

## 0002 – mesh shaders without barycentrics for `xcl.exe`: not suitable

What it does: adds `xcl.exe` to the `MESH_SHADER_WITHOUT_BARYCENTRICS` opt-in that `AlanWake2.exe`
and `ff7rebirth_.exe` have. Without the opt-in, vkd3d-proton turns mesh shaders off as a UE5
workaround when `VK_KHR_fragment_shader_barycentric` is missing, as on RADV on the PS5 (`tools/vkcaps`:
`VK_EXT_mesh_shader 1`, `VK_KHR_fragment_shader_barycentric 0`).

Why not upstream:

- The list holds per-application workarounds keyed by executable name. XCL is a compatibility layer
  whose executable name says nothing about what runs inside it.
- Upstream moved these entries to `libs/vkd3d/vkd3d_proton_app_workarounds.json` in #3488 (merged
  2026-11-18). The C patch does not apply to `master` any more: the C table it edits is gone from
  `device_workarounds.c`.
- What our logs show on the PS5 (`ps5-logs/run6/`): "Detected game xcl.exe, adding 0 configs,
  removing 0 configs." in `vkd3d.log`, XCL's "no mesh shaders" warning (present in `run5`) gone, and
  the test title at 49 of 50 checks in `session.log` (the failure is a window-cloaking check). Not
  tested: drawing anything with a mesh shader on the PS5. The test title has no mesh-shader or NGG
  draws.

Keep it downstream. When the pin moves past #3488, the same opt-in is one JSON entry:

```json

  "applicationFeatures" : [ "MESH_SHADER_WITHOUT_BARYCENTRICS" ],
  "name" : "xcl.exe"
},
```

## 0003 – predicated buffer copies: upstreamable after changes

### What the patch does (against v3.1)

- **Copies under a predicate:** while a predicate is set (`list->predication.va`), `CopyBufferRegion`
  and buffer `CopyResource` no longer call `vkCmdCopyBuffer2`. They call
  `d3d12_command_list_copy_buffer_predicated()` instead, which runs a new meta compute shader,
  `cs_copy_buffer.comp`. The shader works through buffer device addresses (BDA) and copies byte
  ranges, masking the edge words with `atomicAnd`/`atomicOr`.
- **Predicating the dispatch:** the dispatch goes through the existing predication. That is
  conditional rendering, or `d3d12_command_list_emit_predicated_command()` with an indirect dispatch
  when `fallback_enabled` is set.
- **Chunks and barriers:** large copies are split into chunks of 1 GiB, one dispatch each. A memory
  barrier from `ALL_COMMANDS` is placed before the first dispatch, and one to `ALL_COMMANDS` after
  the last.
- **Without a predicate:** unchanged.
- **`ClearState()`:** now calls `d3d12_command_list_update_conditional_rendering_state(list, true)`
  before `reset_api_state()`. `reset_api_state()` clears `list->predication` with `memset`, so
  conditional rendering that was active stayed open on the Vulkan command buffer with nothing left
  to end it. `SetPredication(NULL)` already ends it first (`command.c`, before its `memset`).
  This comes from reading the code. No test exercises it.
- **Test:** a new vkd3d-proton test, `test_conditional_rendering_copy_buffer`.

### Changes needed before submitting

1. **Rebase onto `master`.** The patch was written against v3.1 and has not been built against
   `master`. On `master`, `CopyBufferRegion` still calls `vkCmdCopyBuffer2` unconditionally, so the
   problem is still there.
2. **Split it into three commits:**
   - `vkd3d: End conditional rendering in ClearState().`
   - `vkd3d: Predicate buffer copies with a compute shader.`
   - `tests: Test predicated buffer copies.`
3. **Run the vkd3d-proton tests.** Build with `-Denable_tests=true`. Then run
   `VKD3D_TEST_FILTER=conditional_rendering` (the new test and the existing `test_conditional_rendering`):
   - on NVIDIA and on RADV;
   - and against native D3D12 on Windows, which confirms that D3D12 skips predicated buffer copies.
     So far only XCL's test shows that (it passes on native D3D12 on the same machine,
     `test-native-10.log`).

   None of these has been run: the patch's own message says the test suite was not built in this tree
   (both local build directories have `enable_tests=false`).
4. **Extend the test.** The `CopyResource` part only checks the skipped case. Add one where the
   predicate lets the copy run.
5. **Say what is not covered:** the fallback path without `VK_EXT_conditional_rendering`, texture
   copies, `CopyTiles` and `ResolveSubresource`.
6. **Point out the cost in the description, so the reviewer can judge it:**
   - the barriers are full (`ALL_COMMANDS` / `MEMORY_WRITE`) because the app's barriers only cover
     the COPY stage;
   - when the source and destination offsets differ modulo 4, the shader copies byte by byte;
   - this only happens while a predicate is set.

### Draft PR

**Title:** `vkd3d: Honour predication for buffer copies`

**Description (notes, to be rewritten in your own words):**

- **Problem:**
  - D3D12 predication applies to `CopyBufferRegion` and `CopyResource`, but
    `VK_EXT_conditional_rendering` does not cover transfer commands, so predicated buffer copies
    always ran.
  - `ClearState()` cleared the predicate without ending conditional rendering.
- **Fix:**
  - While a predicate is set, buffer copies run as a small compute dispatch (`cs_copy_buffer`, BDA,
    byte granular). That dispatch is predicated like `Dispatch()`: by conditional rendering, or by
    the indirect fallback.
  - Unpredicated copies still use `vkCmdCopyBuffer2`.
  - `ClearState()` ends conditional rendering before it resets the predication state.
- **How it was found:** a test in XCL (an Xbox Series compatibility layer for Windows) records
  `CopyBufferRegion` calls under `EQUAL_ZERO` / `NOT_EQUAL_ZERO` predicates and reads the destination
  back. On vkd3d-proton it failed with "EQUAL_ZERO(0) must skip dst[0]". The copy that should have
  been skipped had run.
- **Tested:**
  - Windows 11, RTX 3060 Laptop GPU, vkd3d-proton v3.1 with this change and our other downstream
    patches (the vtable check and the dxil-spirv fixes above; MinGW-w64 GCC build,
    `-Db_ndebug=true`): XCL's test failed before the change and passed after it.
  - The rest of XCL's suite on that build had one failure, which also failed before the change.
- **Not tested:**
  - the new vkd3d-proton test (not run yet; see the list above);
  - any non-NVIDIA driver;
  - the fallback path without `VK_EXT_conditional_rendering`;
  - the `ClearState()` change.
- **Not covered:** predicated texture copies, `CopyTiles` and `ResolveSubresource`.

**Reproduction:** `test_conditional_rendering_copy_buffer` in `tests/d3d12_command.c`, as in the
patch:

- an upload buffer `{0x11111111, 0x22222222, 0x33323130, 0x44444444}` is copied into a default buffer

- expected result: `{0xdeadbeef, 0x22222222, 0xdeadbeef, 0x323130ef}`, which includes an unaligned

The evidence behind the "Tested" lines, for our own reference: `test-vkd3d9.log` (failure,
